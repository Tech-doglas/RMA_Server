# Deploy the 16 October 2026 update to fnOS

This package contains source for building Docker images on the NAS. It does not
contain a database, credentials, photos, or the local development configuration.
Use the existing live SQL Server and existing photo mount. This package has not
been deployed to your NAS.

## Changes in this release

- Receive delivery now asks for UPC/Item code, Serial number, Unit photos, and
  Other information per item. Item code/name and Item name are removed from that
  form. Previously stored names are retained.
- Returns and Manage records support full or partial UPC searches.
- UPC and additional information are retained in details, editing, exports, and
  removed-record restoration.
- Company access follows department assignments and action permissions. Review
  these assignments on the server; local settings are not included in the ZIP.

## 1. Extract and build

Save a copy of your current deployment source and keep the old Docker images.
Extract `rma-fnos-source.zip` into your existing deployment directory:
`/vol1/1011/Development/RMA-staging`.
The Compose files must be directly inside that directory. Preserve the existing
`.env`, `data`, and `logs` folders and the mounted production photos.

Keep the working SQL credentials, UID/GID, paths, and connection settings in
`.env`. For production on port 3000, set `RMA_PORT=3000`. Credentials must use
`SQL_USER` and `SQL_PASSWORD`. Do not replace `.env` with `fnos.env.example`.

The commands below use the Compose project name `rma`. The existing NAS folder
can remain `RMA-staging`. Follow the project rename steps below when switching
from the earlier `rma-staging` project.
Run each command separately and stop if any command fails.

```sh
cd /vol1/1011/Development/RMA-staging
sudo docker compose -p rma -f compose.fnos-mssql.yaml config --quiet
sudo docker compose -p rma -f compose.fnos-mssql.yaml build
sudo docker compose -p rma -f compose.fnos-mssql.yaml run --rm --no-deps rma_sql_backend python upgrade_sqlserver.py
```

The last command reports schema gaps without changing SQL. This release requires
`upc`, `itemName`, and `itemInfo` on the existing `RMA_return_receiving` table.
Even though Item name is no longer on the receiving form, the column preserves
earlier records and supports details and editing.

## 2. Upgrade missing columns during maintenance

If the report says the required schema is already present, skip the upgrade
command and continue to section 3.

If columns are missing, arrange a SQL administrator with backup and upgrade
permissions. Keep the normal application login restricted to its existing role;
do not permanently grant it administrative access just to run an upgrade.
See `FNOS_PRODUCTION_UPGRADE.md` for the older legacy schema conversion.

Stop staff activity and all applications writing to this SQL database. Snapshot
or back up `/vol1/1001/RMA/images` separately. Leave SQL Server running.

```sh
sudo docker compose -p rma -f compose.fnos-mssql.yaml stop
```

If the original production containers named `frontend` and `backend` are still
running against the same database, also stop those two application containers:

```sh
sudo docker stop frontend backend
```

Only after all writers are stopped, run the upgrade with the authorized SQL
administrator connection using the existing upgrade procedure:

```sh
sudo docker compose -p rma -f compose.fnos-mssql.yaml run --rm --no-deps rma_sql_backend python upgrade_sqlserver.py --apply --application-stopped
```

The runner creates and verifies a SQL backup before changing the schema. It
includes migrations `012_receiving_upc.sql` and `013_receiving_item_details.sql`.
Already upgraded receiving tables gain the missing columns in place, with blank
defaults; no new receiving table is created. Existing names, IDs, and records are
preserved. Do not run all migration files manually in numerical order.

Restore the normal application SQL credentials if a temporary administrator
connection was used. Continue only after the upgrade reports success.

## 3. Check and start the new application

```sh
sudo docker compose -p rma -f compose.fnos-mssql.yaml run --rm --no-deps rma_sql_backend python -m app.sqlserver_check
sudo docker compose -p rma -f compose.fnos-mssql.yaml up -d --no-build
sudo docker compose -p rma -f compose.fnos-mssql.yaml ps
sudo docker compose -p rma -f compose.fnos-mssql.yaml logs --tail=80 rma_sql_backend frontend
```

Port 3000 must be free before starting the new frontend. If the original
`frontend` container still owns it, stop that old application before `up`.
Keep old application containers stopped after cutover; keep SQL Server running.

Open `http://192.168.68.109:3000/return`, then refresh the browser. Verify login,
existing records and photos, the receiving fields, and UPC search. Use actual
receipts for production writes, not dummy training records.

In Admin > Departments & permissions, verify SnowBell can access only its intended
company and Pc Online only its intended company, with the required action
permissions. An unassigned department sees no company data. Admin accounts can
see every company, so also verify access with an appropriate staff account.

## Rollback and validation

If a check fails, leave the new app stopped and investigate its logs. Keep the
previous source, images, and verified database backup. For a previously upgraded
app, switching back to its saved images may be enough after compatibility review.
Switching back to the original legacy app is different: repeated tracking numbers
may be incompatible. Do not restore an older database over new receipts without
preserving and reconciling intervening writes.

The latest frontend compiled successfully and its receiving UI tests passed.
SQLite tests cover field persistence, existing-data upgrades, editing, exporting,
and restoring records. SQL upgrade-runner and NAS startup tests are also checked
locally. Docker images and the new SQL column migrations still need validation on
your server or a restored SQL copy; a local frontend build does not prove a Docker
image or live SQL deployment works.

## Rename the existing Compose project from rma-staging to rma

A project name change creates containers under the new name; it does not rename
running containers. Preserve the same NAS working directory and .env so relative
bind mounts still reference the existing data, logs, and photo paths. These
commands do not rename the NAS folder or the SQL Server container.

Build and check the new project first:

```sh
cd /vol1/1011/Development/RMA-staging
sudo docker compose -p rma -f compose.fnos-mssql.yaml build
sudo docker compose -p rma -f compose.fnos-mssql.yaml run --rm --no-deps rma_sql_backend python -m app.sqlserver_check
```

If the check fails, resolve it before cutover. After it passes, stop the old
project and start the new one, running each command separately:

```sh
sudo docker compose -p rma-staging -f compose.fnos-mssql.yaml stop
sudo docker compose -p rma-staging -f compose.fnos.yaml stop
sudo docker compose -p rma -f compose.fnos-mssql.yaml up -d --no-build
sudo docker compose -p rma -f compose.fnos-mssql.yaml ps
```

Keep old project containers stopped. If a separate original production frontend
still owns port 3000, stop that old frontend/backend pair before starting rma.
Leave the SQL Server container running. Always use `-p rma` for subsequent builds,
logs, and restarts. This change does not itself require a database migration.
